# Deploying Slipway

Two services, deployed from this GitHub repository:

| Service | Host | Why there |
| --- | --- | --- |
| `backend/` | Render (free) | Needs a real process, not a serverless function. Vercel cannot run the poller or keep a database file. |
| `frontend/` | Vercel | Static and server-rendered Next.js; reads only from the backend. |

The backend ships as a plain Dockerfile, so Railway, Fly.io, Koyeb or a VM work
the same way; only the volume and variable steps differ.

## 1. Backend on Render (free tier)

**What the free tier costs you.** Be clear-eyed about this before choosing it:

- **No persistent disk.** The SQLite database lives on an ephemeral filesystem
  and is lost on every restart, redeploy and wake from sleep. Corridor history
  therefore starts empty each time. Attestations already written to the Soroban
  contract are unaffected: they are on the ledger, not in this database.
- **The service sleeps after 15 minutes of inactivity** and takes about a minute
  to wake. The first request after a quiet spell is slow, and the frontend will
  show "Can't reach Slipway" if it times out first.
- **An in-process cron poller cannot be relied on**, because the service is
  asleep exactly when it should fire. `render.yaml` sets
  `SLIPWAY_POLL_ENABLED=false` and polling is driven externally instead (step 4).
- **750 instance hours a month** per workspace, which one always-awake service
  roughly consumes.

If you later want history that survives, move to a host with a disk (Railway,
Fly.io, Koyeb, a VM) or move the database to Postgres.

### Steps

1. **New → Blueprint** on [Render](https://dashboard.render.com), and point it at
   `slipwaykit/slipway`. Render reads [`render.yaml`](render.yaml), which builds
   [`backend/Dockerfile`](backend/Dockerfile) from the repository root and health
   checks `/api/health`.
2. **Set the two secrets** the blueprint deliberately leaves empty:

   | Variable | Value |
   | --- | --- |
   | `SLIPWAY_ATTESTOR_SECRET` | output of `stellar keys secret slipway`. Required: the app refuses to start in production without it. Never commit it. |
   | `SLIPWAY_CORS_ORIGINS` | your Vercel URL, once you have it. `*` works until then. |

   `SLIPWAY_POLL_TOKEN` is generated by Render; you will copy it in step 4.
3. **Deploy**, then check `https://<your-service>.onrender.com/api/health` returns
   `"status":"ok"` with `"attestorConfigured":true`.
4. **Turn on polling.** In the GitHub repository:
   - **Settings → Secrets and variables → Actions → Secrets:** add
     `SLIPWAY_POLL_TOKEN`, pasting the value Render generated (Environment tab).
   - **→ Variables:** add `SLIPWAY_API_URL` set to your Render URL, with no
     trailing slash.

   [`.github/workflows/poll.yml`](.github/workflows/poll.yml) then calls
   `POST /api/poll` every 15 minutes, which runs one polling pass and keeps the
   service awake. Run it once by hand from the Actions tab to check it. Without
   both values the workflow exits quietly rather than failing.

   GitHub disables scheduled workflows in a public repository after 60 days
   without activity, and scheduled runs can be delayed at busy times.

## Alternative: backend on Railway

Railway is not free (about $5/month after the trial credit), but it gives you a
persistent volume, so history survives restarts and the in-process poller works.

1. **New Project → Deploy from GitHub repo →** `slipwaykit/slipway`. Railway
   reads [`railway.toml`](railway.toml), which points it at
   [`backend/Dockerfile`](backend/Dockerfile) and `/api/health`.
2. **Add a Volume** to the service, mounted at **`/data`**. Without it the
   database is wiped on every redeploy and history starts from zero.
3. **Variables:**

   | Variable | Value |
   | --- | --- |
   | `NODE_ENV` | `production` |
   | `SLIPWAY_ATTESTOR_SECRET` | output of `stellar keys secret slipway`, pasted into Railway's variable editor. Never commit it or put it in chat. |
   | `SLIPWAY_ATTESTATIONS_CONTRACT` | `CBPHQB7YKLPLM7CZWCWUW6QQOBF77QMOTAHHO3PMP25AW4IXUMMSDFMT` |
   | `SLIPWAY_CORS_ORIGINS` | your Vercel URL, once you have it (step 2.4). `*` works until then. |

   `PORT` is injected by Railway and `SLIPWAY_DB_PATH` defaults to
   `/data/slipway.db` in the image. The app **refuses to start** with
   `NODE_ENV=production` and no secret, by design.
4. **Settings → Networking → Generate Domain.** Check
   `https://<domain>/api/health` returns `"status":"ok"` and
   `"attestorConfigured":true`.

## 2. Frontend on Vercel

1. **Add New → Project →** import `slipwaykit/slipway`.
2. **Root Directory:** `frontend`. [`frontend/vercel.json`](frontend/vercel.json)
   sets the install to `pnpm install --frozen-lockfile --filter "frontend..."`,
   which installs the frontend and core only.
3. **Environment variables:**

   | Variable | Value |
   | --- | --- |
   | `NEXT_PUBLIC_SLIPWAY_API_URL` | `https://<railway-domain>` |
   | `NEXT_PUBLIC_SLIPWAY_ATTESTATIONS_CONTRACT` | `CBPHQB7YKLPLM7CZWCWUW6QQOBF77QMOTAHHO3PMP25AW4IXUMMSDFMT` |
   | `ENABLE_EXPERIMENTAL_COREPACK` | `1`, so Vercel uses the `pnpm@12.4.1` pinned in `package.json` |

   `NEXT_PUBLIC_*` values are baked in at build time; changing one needs a redeploy.
4. **Deploy**, then set `SLIPWAY_CORS_ORIGINS` on Railway to the Vercel URL and
   redeploy the backend.
5. Put the live URL in the root README.

## The poll endpoint

`POST /api/poll` exists only when `SLIPWAY_POLL_TOKEN` is set. It requires that
token as a bearer credential, refuses overlapping runs with a `429`, and returns
what the run did. It is a write that fans out to every anchor, so it is never
open. Verified locally on 2026-09-16: `401` without a valid token, and with one,
a real run recording 120 snapshots, with the token absent from the logs.

```bash
curl -X POST "$SLIPWAY_API_URL/api/poll" -H "Authorization: Bearer $SLIPWAY_POLL_TOKEN"
# {"summary":{"corridors":6,"snapshots":120,"successes":7,"attested":0,"failed":[]},"durationMs":4417}
```

## What was verified before this guide was written

Rehearsed on 2026-09-15 in clean copies of the repository, with the exact
install and build commands both hosts run:

- The filtered backend install built the workspace packages without installing
  any frontend dependency; the filtered frontend install built with `next build`
  without installing any backend dependency.
- The rehearsed backend, run as the image runs it (`node --import tsx`,
  `NODE_ENV=production`), refused to start without the secret; with it, it served
  real quotes, returned CORS headers only for the configured origin, and the
  secret appeared in neither `/api/health` nor the server log.

**Not verified:** the Docker image itself was not built (no Docker daemon was
available), and nothing has run on Railway or Vercel yet. The most likely first
snags are Vercel's pnpm version (hence the corepack variable) and a missing
volume on Railway.
